Если отвечать честно и строго по вашему определению (где агент — это когда модель сама выбирает инструменты, а не просто жесткий скрипт по расписанию), то я разделю ответ на две части: продакшн-проект, который сейчас крутится на сервере, и ежедневная разработка, где чистые автономные агенты работают постоянно.

1. СКОЛЬКО АГЕНТОВ РАБОТАЕТ ПРЯМО СЕЙЧАС И ГДЕ

В проде у меня сейчас крутится проект Universal Viral Hunter (система мониторинга трендов, анализа и автопубликации контента). Он развернут на Linux VPS в Docker Compose, работает круглосуточно в фоновом режиме.

В ежедневной разработке на рабочем компьютере у меня постоянно задействована мультиагентная система из 4 специализированных ролей под управлением конфигураций в папке .agent (Orchestrator, Coder, Validator, Healer).

2. ЧТО ИЗ ЭТОГО АГЕНТ, А ЧТО КРОН ИЛИ ПАРСЕР

В продакшн-пайплайне (если по-честному, без хайпа):
Архитектура собрана на LangGraph, и бОльшая часть пайплайна — это как раз детерминированные скрипты и машина состояний, а не свободно блуждающие агенты. И это сделано намеренно ради стабильности и контроля расходов.
- Scout — это парсер по расписанию (крон). Каждые N минут он ходит в X.com через twifork по сессионным кукам, вытягивает посты и дедуплицирует их в SQLite. Единственный элемент AI там — быстрый фильтр релевантности через Gemini, но это просто классификатор, а не агент с тулами.
- Analyst — вообще чистая математика без нейросетей. Обычный Python-скрипт, который по формуле считает Viral Score на основе лайков, репостов, закладок, просмотров и возраста поста.
- Editor — вот это AI-узел. Работает с Gemini. Он мультимодальный: сам анализирует прикрепленные картинки, выбирает наиболее информативную (график, архитектурную схему, код) и пишет структурированный пост на русском языке со строгой JSON-схемой.
- Critic — скриптовый валидатор. Проверяет результат Эдитора на жесткие бизнес-правила (заголовок не длиннее 10 слов, ровно 3 тезиса, наличие хэштегов).
- Связка Editor + Critic образует агентский цикл рефлексии (conditional edge в LangGraph). Если Критик бракует черновик, он возвращает ошибку в граф, и Эдитор перегенерирует контент с учетом замечаний.
- Publisher — скрипт-отправщик в Telegram и менеджер очереди публикаций.

То есть в проде у меня скорее надежная State Machine с циклом рефлексии. Модели намеренно не даны бесконтрольные тулы, чтобы она не галлюцинировала и не сливала баланс API.

А вот в разработке живут настоящие агенты по вашему определению:
Здесь модель сама решает, какой инструмент использовать прямо сейчас: прочитать файл, поискать по коду, применить точечный патч, запустить терминал или выполнить тесты.
- Orchestrator: верхнеуровневый агент. Разбирает задачу, формирует план, следит за контекстом и контрактами.
- Coder: агент модификации кода. Читает AST/файлы, применяет точечные правки.
- Validator: агент контроля качества. Запускает линтеры и тесты через bash.
- Healer: автономный агент починки. Если тесты упали, он перехватывает стек-трейс, изолирует ошибку, сам решает, какой файл подправить, и гоняет цикл до исправления.

3. ИНСТРУМЕНТЫ, ОГРАНИЧЕНИЯ И ПРОВЕРКА ВЫПОЛНЕНИЯ

Для продакшн-узлов (Editor / Critic):
- Инструменты: вызовы Gemini API с переключением моделей (primary/fallback при 429 ошибках), aiohttp для скачивания медиа, Pydantic-валидатор, запись в SQLite.
- Чего делать нельзя: нельзя публиковать напрямую в канал минуя Критика и очередь; нельзя превышать лимиты по токенам и символам; нельзя использовать плейсхолдеры; нельзя падать при 429 ошибке (настроен автоматический rate limiter и fallback).
- Как проверяется задача: Pydantic парсит JSON-ответ модели по строгой схеме. Если схема нарушена или Критик вернул ошибку по бизнес-правилам, узел не завершается успехом, а уходит на повторную попытку. В лог пишется статус каждого этапа.

Для агентов разработки (через .agent / rules):
- Инструменты: файловые операции (view_file, replace_file_content, write_to_file), запуск команд в шелле (poetry run pytest, git diff, ruff), семантический поиск по проекту.
- Чего делать нельзя (у меня прописан жесткий протокол ограничений CFP — Cognitive Friction Protocol):
  * Запрещено без явного подтверждения человека: трогать .env и любые секреты, удалять больше 3 файлов за раз, делать git push в удаленный репозиторий, применять миграции базы данных.
  * Агенту Healer запрещено крутить цикл починки бесконечно: максимум 3 попытки исправить ошибку. Если тесты все еще красные — жесткий стоп и эскалация человеку.
- Как проверяется задача:
  * Прогон тестового набора (poetry run pytest) — код выхода строго 0.
  * Линтинг и отсутствие синтаксических ошибок.
  * Итоговый git diff перед коммитом всегда просматривается глазами.

4. КАК АГЕНТЫ ОБЩАЮТСЯ МЕЖДУ СОБОЙ (И ПРО СВЯЗКУ ФИНАНСЫ -> ПРОДАЖИ)

Внутри пайплайна:
Агенты общаются через общее типизированное состояние LangGraph (AgentState на базе TypedDict). Каждый агент читает только нужные ему поля из стейта и возвращает словарь с обновлениями, которые граф сам мержит. Для списков ошибок используется редьюсер, накапливающий замечания от итерации к итерации.

Между сервисами и запусками:
Связь идет через единую базу данных SQLite, которая выступает персистентной шиной состояний (статусы NEW, PROCESSED, IGNORED, QUEUED, PUBLISHED). Если один контейнер перезагрузится, состояние не потеряется.

В разработке:
Суб-агенты общаются через контекст оркестратора и структурированные отчеты о результатах работы.

По поводу вашей ключевой задачи (передача работы от агента по финансам к агенту по продажам):
Я на практике убедился, что прямой синхронный вызов одним агентом другого (в духе RPC или когда модель напрямую дергает эндпоинт другой модели) для бизнес-процессов — это хрупкая история. Если упадет сеть, кончатся токены или агент продаж зависнет, финансовая транзакция останется в подвешенном состоянии.

Правильный паттерн здесь — асинхронная передача через валидированную шину или очередь событий с гарантией доставки:
1. Агент финансов завершает свою работу, валидирует результат через строгую схему (Pydantic / JSON Schema) и фиксирует факт в надежном хранилище (БД или очередь типа Redis/RabbitMQ/Kafka) со статусом, например, PAYMENT_CONFIRMED и метаданными клиента.
2. Это событие триггерит агента по продажам (через consumer очереди или вебхук).
3. Агент продаж берет уже гарантированно проверенные финансовые данные как неизменяемый инпут (read-only контекст) и начинает свою работу: скоринг клиента, подбор оффера, генерацию персонализированного сообщения или задачи в CRM.
4. Вся цепочка логируется с сквозным trace_id: всегда видно, когда финансы отдали задачу, что именно передали, и где сейчас находится этап продаж. Если агент продаж споткнется, финансовая транзакция не ломается, а задачу по продажам можно безопасно перезапустить из очереди.
